# База данных и резервные копии

## Расположение

По умолчанию: `data/pos.db`. Папку можно изменить переменной `POS_DATA_DIR`.
Рядом создаются `backups/`, `receipts/`, `pos.log`, `crash.log` и `pos.lock`.

SQLite работает без сервера, вся база — один файл. Для работы с базой не нужны
права администратора Windows, но папка данных должна быть доступна на запись.

## Схема

Схема описана в `src/pos/schema.sql`. Версия хранится в `PRAGMA user_version`
(сейчас `2`).

| Таблица | Назначение |
| --- | --- |
| `users` | логин, PBKDF2-хеш пароля, ФИО, роль, активность |
| `user_permissions` | дополнительные права продавца |
| `categories` | категории товаров/услуг, тип и порядок |
| `items` | товары, услуги и расходники; цена, себестоимость, складской учёт |
| `service_consumables` | состав услуг: расходник и количество на единицу услуги |
| `payment_methods` | способы оплаты, влияние на кассу |
| `price_lists` | прейскуранты |
| `price_list_items` | цены позиций в конкретном прейскуранте |
| `shifts` | смены: открытие, закрытие, касса, расхождение |
| `shift_events` | журнал событий смены: открыта, продажа, возобновлена, закрыта |
| `sales` | заголовок чека: номер, смена, продавец, итог |
| `sale_items` | позиции чека со снимком названия, цены и себестоимости |
| `sale_payments` | оплаты чека со снимком способа и признаком кассы |
| `stock_movements` | все движения склада |
| `settings` | настройки приложения (ключ-значение) |
| `import_jobs` | журнал импортов и их результаты |

Представление `item_stock` считает остаток как сумму `stock_movements.qty`
по позиции. Отдельного поля «остаток» у товара нет, поэтому история движений
и текущий остаток всегда согласованы.

### Расходники услуг

- Признак `items.is_consumable = 1` помечает материал, который не продаётся
  отдельно и не показывается продавцу.
- `service_consumables` связывает услугу с расходником и хранит количество
  расходника на одну единицу услуги (`qty`).
- Один расходник может быть привязан к любому числу услуг. Склад у него общий:
  неважно, какая услуга израсходовала материал.
- При продаже услуги создаётся движение склада с типом `consumable` и
  отрицательным количеством. Если материала не хватает, продажа отменяется
  целиком.
- Таблица имеет `ON DELETE CASCADE` для услуги (удаление услуги убирает её
  состав) и `ON DELETE RESTRICT` для расходника (используемый материал нельзя
  удалить).

### Почему снимки

В `sale_items` и `sale_payments` сохраняются название, цена, себестоимость и
способ оплаты на момент продажи. Если позже переименовать товар, изменить цену
или удалить способ оплаты, старые чеки и статистика не изменятся.

## Деньги

Все суммы — целые числа в **копейках**. Это исключает ошибки округления
чисел с плавающей точкой. Например, `15000` — это `150,00 ₽`.
Ввод и вывод форматируются модулем `money.py`; в базе всегда `INTEGER`.

## Транзакции и надёжность

`Database` настраивает соединение так:

- `PRAGMA journal_mode = WAL` — устойчивость к сбоям и параллельное чтение;
- `PRAGMA synchronous = FULL` — подтверждённая транзакция сбрасывается на
  диск и переживает отключение питания;
- `PRAGMA foreign_keys = ON`;
- `busy_timeout = 15000`;
- `isolation_level = None` — транзакциями управляет приложение.

Каждая запись идёт через `BEGIN IMMEDIATE`. Это заранее берёт блокировку
записи и не позволяет двум операциям одновременно изменить одни данные.
Вложенные транзакции реализованы через `SAVEPOINT`.

Пример: создание продажи одной транзакцией записывает заголовок чека, позиции,
оплаты, складские движения и событие смены. Если на любом шаге произойдёт
ошибка, откатится всё — чека без позиций или без оплаты не будет.

## Проверка целостности

- При запуске выполняется `PRAGMA quick_check`.
- Полная проверка `PRAGMA integrity_check` доступна в коде и тестах.
- При повреждении приложение предлагает восстановить базу из последней
  резервной копии. Повреждённый файл не удаляется, а переименовывается в
  `pos-corrupt-<дата>-<время>.db`.
- Если резервных копий нет или восстановление не удалось, приложение
  показывает ошибку и не запускается, чтобы не потерять данные.

## Резервные копии

`Database.backup()` использует SQLite Backup API: копия создаётся согласованно,
даже если база активно используется. Временный файл `.tmp` заменяется
атомарно, поэтому недописанная копия не попадёт в папку.

Копии создаются:

- при запуске приложения (настройка `backup_on_start`);
- перед импортом (`before-import`);
- после закрытия смены (`shift-<id>-closed`);
- вручную из кода/тестов (тег `auto` или свой).

Имя файла: `pos-YYYYMMDD-HHMMSS-<тег>.db`. Хранится от 3 до 200 последних
копий; по умолчанию 20 (настройка `backup_keep`). Старые копии удаляются
автоматически.

### Восстановление вручную

1. Закройте приложение.
2. Скопируйте нужную копию из `data/backups/` в `data/pos.db`.
3. Удалите рядом `pos.db-wal` и `pos.db-shm`, если они остались от старой базы.
4. Запустите приложение и проверьте данные.

Перед заменой сохраните текущий `pos.db` — он может содержать более свежие
продажи, чем копия.

## Миграции

При `user_version = 0` база создаётся из `schema.sql` и получает версию 2.
Версия 1 автоматически обновляется до версии 2: добавляется колонка
`items.is_consumable` и таблица `service_consumables`. Данные и продажи при
этом сохраняются.
Если версия схемы больше поддерживаемой, приложение откажется запускаться,
чтобы не повредить данные новой версии. Для будущих изменений нужно добавить
шаг миграции в `Database._migrate()` и увеличить `SCHEMA_VERSION`.

## Резервное копирование на уровне ОС

Автоматические копии лежат на том же диске, что и база. Для защиты от поломки
диска дополнительно копируйте папку `data/` (или хотя бы `data/backups/`) на
внешний носитель. Копировать базу лучше при закрытом приложении.
